# Решения и допущения

Что решено самостоятельно там, где ТЗ не даёт однозначного ответа, и почему.

## Архитектура

1. **Все правила в базе, клиент тонкий.** ТЗ требует, чтобы права и переходы работали при прямом
   обращении к Supabase. Поэтому единственная точка смены статуса — функция `transition_task()`,
   а правила переходов лежат в таблице `task_status_transitions`. Интерфейс читает ту же таблицу и
   показывает только разрешённые кнопки: нет двух копий бизнес-логики, которые могут разойтись.
2. **Три замка вместо одного.** Привилегии на колонки (нельзя писать в `status` и `author_id`),
   RLS (кто какие строки видит и меняет) и триггеры (статус и история меняются только изнутри
   функции перехода, даже для владельца базы). Любой один слой можно случайно ослабить, три сразу
   сложнее.
3. **Роль хранится в `profiles.role`, а не только в JWT.** Так роль видна в интерфейсе и в SQL, её
   можно поменять в Dashboard без перевыпуска токена. Источник при создании пользователя —
   `app_metadata.role` (его может задать только администратор, пользователь свой `app_metadata`
   менять не может). Если роли там нет, по умолчанию выдаётся наименее привилегированная роль:
   исполнитель.
4. **Облегчённый Feature-Sliced Design** на фронтенде. Для четырёх экранов полный FSD избыточен,
   но разделение entities / features / widgets / pages делает понятным, где что лежит, и не даёт
   компонентам ходить в Supabase напрямую.
5. **Seed через публичный API, а не через SQL.** Демо-данные создаются от имени реальных
   пользователей через те же RLS и `transition_task()`. Это одновременно сквозная проверка, что
   защита не мешает нормальным сценариям.

## Доменные допущения

6. **Задачу можно создать без исполнителя** и назначить позже. Взять такую задачу в работу никто
   не может, пока постановщик не назначит исполнителя.
7. **Исполнителем может быть только пользователь с ролью «Исполнитель».** Проверяется триггером.
   Постановщик не может назначить задачу себе или другому постановщику.
8. **Переназначить исполнителя можно в любом статусе.** История статусов при этом не меняется:
   она фиксирует только смены статуса, как требует ТЗ. Прежний исполнитель теряет доступ к задаче
   (и к объекту, если других его задач там нет).
9. **Постановщик может редактировать название, описание и исполнителя в любом статусе**, включая
   принятую задачу. Ограничивать это ТЗ не просит, а в жизни опечатку в названии правят и после
   приёмки.
10. **«Принята» — терминальный статус.** Из него переходов нет. Если задачу нужно переделать,
    постановщик создаёт новую.
11. **Комментарий обязателен только при возврате на доработку** (как в ТЗ). Для остальных переходов
    комментарий не предусмотрен интерфейсом, хотя функция его принимает: расширить легко.
12. **Удаление задачи удаляет и её историю; удаление объекта удаляет его задачи.** История
    «неизменяема» в смысле ТЗ: её нельзя подделать, изменить или удалить через API как отдельную
    сущность. Триггер разрешает удаление записи истории только каскадом вместе с задачей. Если
    бизнесу нужен след и после удаления, следующий шаг — soft delete (`deleted_at`) вместо
    физического удаления; это сознательно не делалось в рамках 2–3 часов.
13. **Пользователей не удаляют.** `tasks.author_id` и `task_status_history.actor_id` ссылаются на
    профиль без каскада: удалить пользователя с историей действий база не даст. Уволенного
    сотрудника логично деактивировать (забанить в Supabase Auth), а не удалять.
14. **Имена и роли всех пользователей видны всем вошедшим.** Это нужно, чтобы показать автора
    задачи и выбрать исполнителя. Контактных данных в `profiles` нет; email виден только самому
    пользователю через Auth.
15. **Исполнитель на карточке объекта видит только свои задачи**, а в списке объектов — только
    объекты, где у него есть задачи. Счётчик задач у объекта тоже считает только видимые ему задачи.
16. **Исполнитель, запрашивая чужую задачу, получает «не найдена», а не «запрещено».** Так он не
    может даже узнать, что задача существует.

## Что не вошло и что бы сделал следующим

- **Realtime-обновления.** Списки обновляются после действий пользователя и при повторном заходе;
  подписки на изменения не делал, в ТЗ их нет.
- **Пагинация и поиск.** На объёмах тестового задания не нужны; для сотен задач добавил бы серверную
  пагинацию через `range()` и фильтр по статусу на стороне базы.
- **Soft delete** для задач и объектов (см. п. 12).
- **Смена роли через интерфейс администратора.** Сейчас роль меняется в Supabase Dashboard
  (`profiles.role` или `app_metadata.role`).
- **Code splitting.** Бандл один (~270 КБ gzip), для такого приложения приемлемо; при росте разбил бы
  по страницам через `React.lazy`.
- **E2E-тесты интерфейса (Playwright).** Логика защиты покрыта pgTAP на уровне базы (61 тест),
  клиентский расчёт доступных действий — Vitest; сценарии кликов проверялись руками.
