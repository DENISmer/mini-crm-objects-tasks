# Мини-CRM «Объекты и задачи»

Небольшая CRM для строительной компании: постановщики заводят объекты (стройки) и задачи по ним,
исполнители берут задачи в работу и отдают на проверку. Каждая смена статуса попадает в неизменяемую
историю. Правила доступа и переходов работают на уровне базы данных, а не только в интерфейсе.

- Стек: React 19 + TypeScript (Vite), Supabase (Postgres, Auth, PostgREST), shadcn/ui + Tailwind,
  TanStack Query, react-hook-form + zod.
- Тесты: pgTAP для прав доступа и машины состояний (`supabase/tests`), Vitest для клиентской логики.
- Документы сдачи: [docs/HANDIN.md](docs/HANDIN.md) (сообщение для сдачи: доступы, объяснение для
  руководителя, краткие решения), [docs/DECISIONS.md](docs/DECISIONS.md) (полный список решений и допущений).

## Как устроено

**База отвечает за правила, клиент только отображает.** Пять миграций в `supabase/migrations`:

| Файл                            | Что делает                                                                                                                                        |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `..._schema.sql`                | Таблицы `profiles`, `objects`, `tasks`, `task_status_history` и справочник переходов `task_status_transitions`                                    |
| `..._profiles_and_triggers.sql` | Профиль создаётся автоматически при появлении пользователя; роль берётся из `app_metadata`                                                        |
| `..._task_workflow.sql`         | RPC `transition_task()` — единственный способ сменить статус; триггеры-«замки» на статус и историю                                                |
| `..._rls.sql`                   | Привилегии ролей (включая запрет писать в колонку `status`) и RLS-политики                                                                        |
| `..._explicit_privileges.sql`   | Явные права `service_role` и снятие дефолтного EXECUTE для `PUBLIC`: облачный Supabase с 2026 года не выдаёт права на новые таблицы автоматически |

Защита в три слоя, каждый работает при прямом обращении к Supabase API:

1. **Привилегии на колонки.** Роль `authenticated` не может писать в `tasks.status` и `tasks.author_id`
   вообще: прямой `PATCH` статуса отбивается до RLS.
2. **RLS.** Исполнитель видит только свои задачи и объекты, где у него есть задачи. Создавать,
   редактировать и удалять объекты и задачи может только постановщик.
3. **Функция перехода и триггеры.** `transition_task(task_id, to_status, comment)` сверяется со
   справочником переходов, проверяет роль, назначение и обязательность комментария, затем атомарно
   меняет статус и пишет историю. Триггеры запрещают менять статус и историю в обход функции даже
   владельцу базы и `service_role`.

Интерфейс читает тот же справочник переходов и показывает только те кнопки, которые база разрешит
(`src/entities/task/lib/available-transitions.ts`).

## Запуск локально

Нужны Node.js 22+ (есть `.nvmrc`), npm и Docker (для локального Supabase).

```bash
npm install
```

```bash
npx supabase start
```

Команда выведет `API URL`, `anon key` и `service_role key` локального стека. Скопируйте
`.env.example` в `.env.local` и подставьте URL и anon key:

```bash
cp .env.example .env.local
```

Запуск приложения:

```bash
npm run dev
```

### Демо-данные

Скопируйте `.env.seed.example` в `.env.seed.local`, заполните URL, anon key, service_role key и
пароль для тестовых пользователей, затем:

```bash
npm run seed
```

Скрипт создаёт пользователей через Admin API (регистрация в проекте закрыта), а объекты, задачи и
переходы статусов делает **через обычный API от имени этих пользователей**, то есть проходит те же
RLS и `transition_task()`, что и интерфейс. Повторный запуск данные не дублирует, а пароли
демо-пользователей подтягивает к текущему `SEED_PASSWORD`.

## Тесты

```bash
npm test
```

```bash
npm run test:db
```

`test:db` запускает pgTAP-тесты против локальной базы: права доступа каждой роли, все разрешённые и
запрещённые переходы статусов, неизменяемость истории, создание профилей. Тесты выполняются в
транзакции и откатываются, поэтому их можно запускать на базе с данными.

## Облачный Supabase и деплой

Рабочий экземпляр: <к>. Демо-пользователи из таблицы выше.

1. Создайте проект на [supabase.com](https://supabase.com). В **Authentication → Sign In / Providers**
   выключите _Allow new users to sign up_.
2. Примените миграции:

```bash
npx supabase login
```

```bash
npx supabase link --project-ref <project-ref>
```

```bash
npx supabase db push
```

3. Создайте `.env.seed.cloud.local` со значениями облачного проекта (URL, anon key, service_role
   key, пароль демо-пользователей) и выполните:

```bash
SEED_ENV_FILE=.env.seed.cloud.local npm run seed
```

Файлы `*.local` в репозиторий не попадают, service_role key нигде, кроме них, не хранится. 4. Задеплойте фронтенд, задав переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`:

- **Vercel**: импорт репозитория, фреймворк Vite определяется автоматически, `vercel.json`
  содержит SPA-rewrite.
- **Railway**: сервис из репозитория собирается по `Dockerfile` (nginx с SPA-fallback, порт из
  `$PORT`). Переменные сервиса автоматически подставляются в сборку.

Пользователей можно создавать и вручную в **Authentication → Users**. Такой пользователь получит роль
исполнителя; чтобы сделать его постановщиком, поменяйте `role` в таблице `profiles` или добавьте
`{"role": "manager"}` в его app metadata.

## Структура кода

Облегчённый Feature-Sliced Design: слои зависят только «вниз».

```
src/
  app/        провайдеры, роутер, глобальные стили
  pages/      экраны: вход, объекты, объект, задача, «мои задачи»
  widgets/    составные блоки: шапка приложения, таблица задач, история
  features/   действия пользователя: auth, формы объектов и задач, переходы статусов
  entities/   доменные сущности: типы, API-слой поверх Supabase, query-хуки
  shared/     клиент Supabase, сгенерированные типы, UI-кит (shadcn), утилиты
```

Компоненты не обращаются к Supabase напрямую: только через `entities/*/api.ts`.
